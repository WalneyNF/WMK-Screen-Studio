Manual de servidor para reuniões e aulas

WMK Meeting Studio / Classroom Studio · Explicação passo a passo, do básico ao primeiro teste com celular.

README · Plano pedagógico · Roadmap

1. O que é um servidor?

Servidor é um computador, físico ou virtual, que hospeda um serviço e responde a conexões pela rede. Nas videoconferências, ajuda a organizar a sala e encaminhar áudio/vídeo entre os participantes. Não é necessário comprar um computador especial: uma VPS na internet pode executar o serviço.

WebRTC: tecnologia usada para transportar mídia em tempo real. Jitsi: software de videoconferência. VPS: computador virtual alugado. Docker: ferramenta que executa componentes do servidor em containers. DNS: aponta um domínio para o endereço IP. HTTPS: conexão web protegida por certificado. TURN: retransmissão de mídia quando redes e firewalls impedem conexão direta.

3. Primeiro teste sem servidor próprio

  1. Abra meet.jit.si.
  2. Digite um nome de sala único e entre. O organizador pode precisar autenticar-se no serviço público.
  3. Permita câmera e microfone se desejar.
  4. Compartilhe o link completo com um segundo computador ou celular.
  5. Teste o áudio bidirecional, câmera, reconexão e uso com internet móvel. Experimente também com câmera desligada para reduzir consumo de rede.

Para aulas e reuniões confidenciais, verifique as políticas e controles reais do provedor público. Não considere o endereço aleatório uma senha.

4. Planejando uma VPS

Escolha um VPS com IP público, Ubuntu/Debian suportado, backup e capacidade de tráfego adequada. Para um laboratório pequeno, um ponto de partida a avaliar é 4 vCPU e 8 GB de RAM, sem garantia de capacidade: participantes, codecs, número de câmeras e qualidade influenciam muito o uso. Comece com uma turma pequena e monitore CPU, RAM e rede.

Defina um domínio próprio, por exemplo meet.exemplo.com.br. No painel DNS do registrador, configure um registro A apontando esse nome ao IP público do servidor. Configure AAAA somente se IPv6 estiver realmente pronto. Aguarde a propagação DNS.

5. Instalação Docker — roteiro seguro

Este é um roteiro de instalação nova, não um script automático que cobre todos os casos. É necessário primeiro instalar Docker Engine e Docker Compose v2 seguindo o sistema operacional do VPS. Use a release estável do projeto docker-jitsi-meet, não um pacote de origem desconhecida.

  1. Confirme domínio e IP público e planeje SSH de administração com chave.
  2. Instale Docker Engine e Compose conforme a documentação de sua distribuição.
  3. Baixe uma versão estável do docker-jitsi-meet e extraia no diretório escolhido.
  4. Na pasta extraída, crie o arquivo .env a partir de env.example.
  5. Configure PUBLIC_URL, portas, certificado HTTPS e endereço de mídia de acordo com a sua rede.
  6. Gere senhas internas com ./gen-passwords.sh e proteja .env.
  7. Verifique a configuração com docker compose config, sem publicar os segredos.
  8. Suba os containers e confira logs/estado.
  9. Teste chamadas reais com pelo menos dois dispositivos em redes diferentes.

Consulte as instruções oficiais para gerar senhas, ajustar as variáveis e preparar diretórios de configuração: manual de Docker do Jitsi.

Exemplos básicos de comandos na pasta do projeto

docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs --tail=80 web
docker compose logs --tail=80 jvb

Os comandos pressupõem arquivos corretos, DNS, certificado e firewall configurados. Não copie variáveis de exemplo sem ajustá-las e não divulgue o arquivo .env.

6. Portas, firewall e HTTPS

Porta típicaProtocoloFunção
80TCPRedirecionamento HTTP ou validação de certificado, se configurados
443TCPSite e sinalização HTTPS
10000UDPMídia (Jitsi Videobridge), quando usa porta padrão
22 ou outraTCPAdministração SSH, idealmente restrita a IP/VPN autorizado
3478/5349 e outrasUDP/TCPSTUN/TURN quando configurados, não liberar por reflexo

Verifique também o firewall do provedor de nuvem e as regras do Docker. Não habilite UFW remotamente sem preservar acesso SSH. Para acesso de celulares, prefira certificado HTTPS válido; certificados autoassinados frequentemente causam problemas.

7. Perfis, convite e proteção

Uma página web WMK pode ajudar a gerar convite, mas não concede efetivamente papéis de professor/moderador. Isso deve ser validado no servidor com autenticação, lobby e permissões. Não coloque tokens de administração em HTML público. Os alunos poderão receber link pelo WhatsApp/e-mail e entrar com navegador ou aplicativo compatível; dispositivos móveis podem variar por sistema e política do servidor.

Em produção: política de senhas, atualizações, backups, logs com retenção limitada, monitoramento, controle de gravação e tratamento de dados pessoais. Para crianças e adolescentes, avaliar requisitos adicionais de proteção, supervisão e acesso.

8. Diagnóstico de problemas comuns

SintomaInvestigação
Site não abreVerificar DNS, IP, HTTPS, certificado, 443/TCP e serviço web
Site abre, mas ninguém se ouveVerificar 10000/UDP, JVB, endereço anunciado/NAT, permissões de microfone e TURN
Funciona com 2, falha com maisVerificar caminho de mídia pelo Videobridge, não apenas conexão P2P
Celular recusa a entradaVerificar HTTPS, navegador/app, permissões e sala de espera
Vídeo trava ou áudio cortaMedir perda de pacotes, banda, carga de CPU e qualidade solicitada
Qualquer pessoa cria salasConfigurar autenticação para criação e controle de moderadores

9. Como isso se integra ao WMK

Fase 1: página de convite responsiva abrindo salas gerenciadas pelo Jitsi. Fase 2: integração no WMK Desktop para gerenciar convidados, layouts e gravações autorizadas. Fase 3: Classroom com tarefas, enquetes, quadro branco, IA pessoal configurável e relatórios. Essas fases são planejadas e não equivalem a uma solução de videoconferência pronta no WMK.
